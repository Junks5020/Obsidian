# ADR-0008：生成走异步任务，前端轮询，定时回收卡死任务

部署在托管 serverless 环境（ADR-0007），而 image-edit 通常需要十秒以上，同步等待会让用户刷新即丢结果。已有 schema 的 `status` 枚举本就按异步设计。

决定：`POST` 创建 `pending` 记录后立即返回；后台执行；**前端轮询 `status`** 直到终态。另设定时任务扫描卡死记录（既包括超时的 `processing`，也包括长期停在 `pending` 的），判 `failed` 并退回 credits。

**执行载体与函数最长执行时长尚未确定**：是靠请求生命周期内的后台执行、还是独立运行时/定时任务触发，需按托管商当前官方文档与套餐确认。本 ADR 只锁定"异步 + 轮询 + 超时回收"这个形状，不锁定具体机制。

## 后果

- **必须有超时回收**。没有它，执行中途被杀后记录会永久停留，用户额度也永久不回。这是本设计里最容易漏的一环。
- 靠请求生命周期内的后台执行本身不可靠：该机制能否在响应结束后继续跑，必须查文档确认。若不成立，改为由定时任务触发执行，**而不是**改回同步等待。
- 需要记录"进入 processing 的时刻"（独立字段或复用 `updated_at`），否则无法判断超时。
- 终态迁移必须幂等：重复执行、重复回收、重复退款都不能造成二次扣/退。退款必须与终态原子关联，且**不得以客户端可修改的字段为凭据**（见 spec 的额度安全约束）。
- 一期不引入消息队列、不用 Supabase Realtime；轮询间隔约 1.5s，量级是几十人，够用。
- **回收必须分两层**：托管平台免费套餐的 cron 粒度通常是"每天一次"，单靠 cron 会让用户超时后干等最长一天。因此轮询路径要在发现超时时即时触发 `reapOne(id)`，cron 只做每日兜底 `reapStale()`。这条是实施时对"定时回收"的必要修正，不改变决策形状。
- 用户可离开页面再回来查看历史，这是异步带来的正向副产品，应体现在产物页上。

## 实施后发现（2026-10-30）

第二层回收上线前被验收审查发现**从未真正执行**：`/api/cron` 不在 middleware 的公开路径白名单里，而平台定时调度请求不带会话 Cookie，因此每次都被 307 到 `/login`，路由自己的 `CRON_SECRET` 校验根本走不到。

教训写在这里而不是留在代码注释：**新增任何"无会话的服务端入口"时，必须同时检查中间件白名单**，否则该入口是死代码，而且不会有任何报错提示。已修复并补进 `.env.example` 的 `CRON_SECRET`。
