# 保持功能型同步并深化树拓扑与筛选提交模块

相关：[[report-table-功能型同步架构重构计划-20260810]] · [[report-table-ADR-0001-跟随上游功能型同步]] · [[report-table-同步术语表]]

原始规格：[GitLab #1](http://gitlab.newgrand.com/newgrand.techcenter/map/ng-design/-/issues/1)

## Problem Statement

`udp-report-table` 需要持续跟随 `report-web:6.5.2-dev` 做功能型同步，但当前树结构与筛选行为分散在多个模块中：树渲染和筛选范围各自解释 `children`、`treeParent`、`treeLevel`、`showLevel` 及响应 cells；一次筛选提交又横跨 loading、store、cells、全局设置、树状态和预览可见性，并依赖调用者掌握严格顺序。

这种结构使同一条上游功能血缘在本地存在多个事实来源。同步树筛选、折叠或可见性修复时，维护者容易只修改其中一处，造成回归；为横向和纵向筛选追求表面对称，还可能把当前不可达或未被上游确认的行为意外变成新功能。

用户需要的是重构后功能保持不变：上游血缘行为继续与固定上游基线等价，7.0 原生行为继续保持当前表现，公共 API 不发生变化，且后续上游同步可以在更少、更明确的模块边界内完成。

## Solution

采用双基线、分阶段的内部重构：先以固定的 `report-web:6.5.2-dev` commit 建立 parity fixtures，并以当前 7.0 characterization tests 保护原生行为；随后引入不可变的报表树拓扑模块，统一配置树元数据与响应 cells 的解释；再引入包内筛选提交事务，通过 adapter 收拢成功路径中的 store 与 Handsontable 副作用。

两个模块均保持包内，不增加公开导出，不改变 props、事件或数据结构。既有 bug、失败回滚和 visibility owner 修复不夹带在架构提交中。轴向无关筛选计算只做证据调查，必须同时证明横向入口可达、属于上游功能血缘并拥有行为基线，才进入独立实现。

## User Stories

1. 作为报表预览用户，我希望重构前后的报表内容一致，以便无需感知内部架构变化。
2. 作为树报表用户，我希望初始展开层级保持一致，以便 `showLevel` 配置继续按原有方式生效。
3. 作为树报表用户，我希望展开和收起节点后显示的行保持一致，以便继续可靠浏览层级数据。
4. 作为树报表用户，我希望断裂或不完整的树元数据仍按现有兼容规则显示，以便历史报表不会因重构失效。
5. 作为报表筛选用户，我希望单条件纵向筛选结果保持一致，以便继续得到相同数据集合。
6. 作为报表筛选用户，我希望多条件级联筛选结果保持一致，以便组合条件不会因规则迁移改变。
7. 作为报表筛选用户，我希望重置筛选恢复相同的数据与可见性状态，以便筛选操作可逆。
8. 作为父子树筛选用户，我希望完整筛选范围仍能从树元数据和响应数据中正确证明，以便目标列不会漏筛或越界筛选。
9. 作为多列树报表用户，我希望后续列的筛选范围继续复用已证明的展开范围，以便级联筛选保持与上游一致。
10. 作为报表设计用户，我希望持久隐藏的行列在筛选或树展开后仍遵循既有行为，以便设计结果不会被内部刷新意外改变。
11. 作为报表预览用户，我希望树折叠隐藏和筛选隐藏继续组合生效，以便一种操作不会错误显示另一种操作隐藏的数据。
12. 作为报表预览用户，我希望筛选成功路径中的 loading 表现保持一致，以便交互反馈不发生变化。
13. 作为报表预览用户，我希望筛选后的 cells、排序和渲染结果保持一致，以便页面视觉与数据语义稳定。
14. 作为组件使用方，我希望公开组件、类型、props 和事件保持不变，以便现有集成无需修改。
15. 作为组件使用方，我希望 Handsontable 继续被封装在组件边界内，以便集成代码不依赖内部实现。
16. 作为 7.0 功能使用者，我希望条形码、ribbon、字体、data 模式等原生能力不受影响，以便独立需求线继续演进。
17. 作为组件使用方，我希望卸载时的 `destroy` 清理继续保留，以便反复挂载和卸载不会引入资源泄漏。
18. 作为上游同步维护者，我希望树事实只在一个模块中解释，以便同步树相关修复时不再寻找多份镜像逻辑。
19. 作为上游同步维护者，我希望每次重构绑定明确的上游 commit，以便 parity 结论可复现、可审计。
20. 作为上游同步维护者，我希望重构阶段之间单独复核新增上游提交，以便同步变化不会和架构变化混为一个 diff。
21. 作为代码维护者，我希望报表树拓扑是纯计算且不可变的，以便无需运行 UI 就能验证复杂树规则。
22. 作为代码维护者，我希望拓扑模块不持有 store 或 Handsontable，以便其生命周期和副作用边界清晰。
23. 作为代码维护者，我希望筛选提交由一个包内入口编排，以便调用者无需了解 loading、reload、tree、visibility 和 render 的顺序。
24. 作为代码维护者，我希望 store 与 Handsontable 操作经由 adapter 隔离，以便测试最终行为而不依赖真实 DOM。
25. 作为代码审查者，我希望每个提交都独立通过测试并可回退，以便审查和故障定位保持小范围。
26. 作为代码审查者，我希望架构提交不夹带既有 bug 修复，以便行为变化能够单独评估。
27. 作为测试维护者，我希望复用现有 `node:test` 体系，以便不增加新的测试框架和运行成本。
28. 作为测试维护者，我希望主要从现有调用入口验证行为，以便测试不与内部 helper 结构绑定。
29. 作为测试维护者，我希望公共边界测试持续验证导出契约，以便包内重构不会扩大 API。
30. 作为后续实施 agent，我希望规格明确停止条件和功能血缘，以便遇到同步缺口时不会自行猜测并继续重构。
31. 作为横向筛选使用者，我希望只有已被上游确认且当前可达的横向行为才被抽象，以便重构不会意外创造新功能。
32. 作为产品维护者，我希望候选三即使不实施也留下证据化结论，以便以后出现真实需求时知道重新评估的触发条件。

## Implementation Decisions

- 上游功能基线固定为 `report-web:6.5.2-dev` 的 `6636f93207d701517e78de9af46cc8dd57548fda`；目标起点固定为当前 `sync_branch` 的 `2114199ab95244262404e76ac8776aca3b0fa0d2`。
- 有上游功能血缘的行为使用 parity fixtures 验收；7.0 原生行为使用当前 characterization tests 验收。两类基线必须同时保持绿色。
- 开始架构重构前先审计固定上游基线与目标实现。发现未登记的同步差异时停止重构，创建独立同步工作项。
- 第一阶段深化报表树拓扑，第二阶段深化筛选提交与预览可见性；阶段之间不混入新的上游同步提交。
- 报表树拓扑是可重建的不可变快照，统一合并配置树元数据与响应 cells，并提供标准化节点、父子索引、初始折叠、隐藏行和筛选范围证明。
- 拓扑模块不持有 Handsontable、store、cell meta 或其他 UI 状态，不引入全局缓存或新的 `WeakMap`。
- 树交互 adapter 继续拥有折叠交互状态和 UI 副作用；筛选范围保留筛选领域适配，但不再独立解释树事实。
- 筛选提交事务只封装现有成功路径，包括延迟、loading、筛选计算、cells 与全局设置重载、树状态重建、当前筛选 owner 应用、render 和 loading 结束。
- 筛选事务通过包内 adapter 访问 store 与 Handsontable，使副作用顺序可以在不运行真实 UI 的情况下验证。
- 本次重构不新增失败回滚、重试、吞错或错误恢复语义。
- 是否保留全部 visibility owners 必须由固定上游基线证明。若现状错误清除其他 owner，作为独立 bug 处理。
- 新模块均保持包内，不新增 runtime 或 type exports，不改变 props、事件和持久化数据结构。
- 旧调用点逐个迁移；只有迁移完成且双基线通过后，才删除重复实现。
- 代码工作拆为可独立验证和回退的小提交：基线 fixtures、拓扑模块、树调用迁移、筛选范围迁移、重复树逻辑删除、事务 adapter 与测试、筛选入口迁移、旧事务编排删除。
- 轴向无关筛选计算默认不实施。只有横向调用路径可达、上游功能血缘成立、横向行为 fixtures 完整三项同时满足，才另开实现规格。
- Obsidian 继续作为 ADR、术语表和架构计划的唯一持久来源；GitLab issue 负责规格、tickets、状态和依赖。

## Testing Decisions

- 好测试验证用户可观察结果和稳定契约，不验证内部 helper 数量、私有函数命名或无行为意义的调用细节。
- 主行为 seam 复用现有调用入口：树初始化、树筛选范围标准化和筛选渲染入口。测试迁移前后的最终 cells、范围、折叠集合、隐藏集合和 loading 成功路径。
- 新增的纯计算 seam 是报表树拓扑模块。直接测试配置与响应来源合并、显式与推断父子关系、无效值、重复节点、断裂树、`showLevel` 和范围证明。
- 公共契约 seam 复用现有 boundary tests，持续验证公开 runtime/type exports、组件契约和 Handsontable 隔离边界。
- 筛选副作用测试只断言会改变结果的关键顺序，例如重载设置后重建树状态，再应用筛选 owner；不锁定每一次内部调用。
- 上游 parity fixtures 至少覆盖父子树完整范围、多列级联筛选、树折叠、持久隐藏与 tree/filter 隐藏叠加。
- 7.0 characterization fixtures 继续覆盖原生行为和唯一有意偏离的卸载清理。
- 沿用现有 `node:test` 测试加载方式，不引入 Jest、Vitest 或新的 DOM 测试框架。
- 每个迁移提交运行聚焦行为测试与公共边界测试；每个阶段结束运行全部现有测试、TypeScript 检查、包构建和 diff 格式检查。
- 当前 prior art 是现有功能同步测试、迁移 parity 测试、打印 payload 测试和包边界测试；规格建立时共 54 项测试通过，TypeScript 检查通过。
- 不允许提交处于红灯状态并依赖后续提交恢复；若一个提交无法独立保持绿色，必须继续缩小范围。

## Out of Scope

- 不新增或移除用户功能。
- 不修复重构过程中发现的既有 bug；这些问题单独登记、复现和修复。
- 不改变公开 API、props、事件、数据结构或包导出。
- 不改变 7.0 原生功能的独立演进规则。
- 不移除 7.0 卸载 `destroy` 清理。
- 不实现新的失败回滚、重试、错误恢复或 loading 语义。
- 不默认修复或保留全部 visibility owners，除非上游 parity 证据明确要求。
- 不引入全局拓扑缓存、新状态容器或新测试框架。
- 不为了代码对称性实现轴向无关筛选计算。
- 不在源码仓库复制 ADR、术语表、调查记录或重构计划。
- 不在本规格中处理新的上游同步提交；阶段复核发现的变化使用独立同步 ticket。

## Further Notes

- 已知目标分支存在与上游树筛选、父子树范围、行列隐藏和性能修复对应的同步提交，但提交映射只证明功能血缘，不替代固定基线的行为审计。
- 上游是移动目标。每阶段完成后检查固定 SHA 之后涉及树、筛选或可见性的提交；先保持当前阶段绿色，再决定是否新增同步 ticket 和更新基线。
- 第一张实施 ticket 必须是固定基线审计与 fixtures，它阻塞后续架构 tickets。
- 候选三的调查结论保存在 Obsidian。若没有产生行为 fixture 或实现，不在源码仓库创建空提交或调查文档。
- 停止条件包括：发现未登记同步差异、需要改变公共 API、visibility owner 语义无法证明、提交无法独立保持绿色。
- 相关长期决策和术语已经记录在项目 Obsidian 的功能型同步 ADR、同步术语表和架构重构计划中。
