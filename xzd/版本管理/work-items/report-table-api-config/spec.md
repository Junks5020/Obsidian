- 用户选择兼容策略 A：保留现有读取设计、保存设计、计算预览三个 `apiExecutor` 的兼容性，已有接入方式继续有效。
- 用户选择双配置规则 A：同一接口配置了 `apiExecutor` 时执行器优先，新 URL、请求转换和响应转换全部不参与；没有执行器时才使用新配置路径。
- 用户确认 URL、请求转换、响应转换可分别独立配置；未配置的部分保持现有行为。例如只改 URL 时，请求参数、响应处理及业务逻辑保持原样。
- 用户选择请求转换语义 A：转换函数的返回值完全替换原参数，不自动合并。字段重命名后不再发送旧字段；需要保留的字段由转换函数显式保留。转换函数忘记返回值或返回内容不符合该接口契约时直接报错，不恢复原参数；合法空数据按接口契约接受，不一概拒绝 `null`、空数组或空对象。
- 用户明确不允许通过新配置修改 HTTP 方法、请求头或参数在 query/body 中的放置方式：这些沿用既有接口行为，请求转换仅修改参数内容。此限制针对新配置，不收窄已确认保留的 `apiExecutor` 能力；本需求不承诺适配任意后端协议。
- 用户确认响应转换可处理整个接口结果，包括成功标识、错误消息和业务数据，转换后继续现有业务处理；各接口适配回各自原有的结果契约，不强制统一响应格式。此处结果指请求层交给组件 service 的结果，不承诺原始 HTTP Response。
- 用户接受按组件实例独立传入配置，各实例互不污染；需要共用时，宿主可向多个实例传入同一份配置对象。配置 prop 为 `apiConfig`，采用“接口标识 → `url` / `transformRequest` / `transformResponse`”的结构。

- 用户确认无效转换结果直接报转换错误，不恢复使用原值：请求转换错误时不发送请求；响应转换错误时不继续业务处理、不重发。合法空数据按对应接口契约接受。

## 已确认参数通道限制

**首版不得通过新配置增加原接口没有的参数通道。用户已于 2026-10-29 整体确认此限制。**

例如原接口仅发送 JSON body 或 FormData，则配置 URL 不可额外添加 query，发现时应报配置错误，而不是忽略、把字段塞进 body、动态改变转换函数形状或回退默认接口。原本具备 URL query 通道的接口，可以在 query 内增删改字段；原本同时有 query 与请求数据的接口，继续使用 `{ query, data }`。

理由：保持已确认的单通道直接入参、FormData 直接入参、混合通道固定入参三种契约稳定，也遵守不开放参数位置修改的边界。若需要允许新增通道，必须重新明确转换签名，不能由实现自行猜测。

## 已确认配置结构

用户已接受实例级 `apiConfig`，采用“接口标识 → `url` / `transformRequest` / `transformResponse`”的结构。配置结构、混合参数形状、文件请求形状、无效返回值处理及 URL-query 优先级已逐项确认。

```tsx
<DesignReportTable
  apiConfig={{
    findReportDesignDetail: {
      url: '/custom/report/detail',
      transformRequest: ({ id }) => ({ reportId: id }),
      transformResponse: (res) => ({
        Code: res.success ? 200 : 500,
        Msg: res.message,
        Data: res.result
      })
    }
  }}
/>
```

此示例假设新后端的 `res.result` 已满足原读取接口的 `Data` 契约，否则须在响应转换中继续适配。按业务接口标识配置，而不是以 URL 字符串作为配置键；当前 36 项标识及重复入口见关联覆盖清单。

## 已确认混合参数契约

只有一处参数的普通接口继续直接接收参数对象。同时包含 URL query 与请求数据的接口采用以下形状：

```ts
transformRequest: ({ query, data }) => ({
  query: { ...query, node: 'custom-root' },
  data: { condition: data.condition }
})
```

返回的 `query`、`data` 分别完整替换原来的两部分，不自动合并。模块保持该接口既有参数通道及编码方式；不开放 `method` 或 `headers` 配置。

## 已确认文件请求契约

图片上传、报表及打印模板导入的 `transformRequest` 接收并返回 `FormData`，包含真实文件及附加字段，允许重命名、增删字段。返回的表单完全替换原表单，不自动补回已删除字段；传输方式保持不变，不自动转 JSON。

导出接口的普通请求参数不因该规则改为 FormData。下载响应仍须适配回原有消费结构。

## 已确认 URL-query 优先级

自定义 URL 自带 query 时，先合并原 URL query 与运行时查询参数，再叠加自定义 URL query（同名项以自定义值为准），然后交给 `transformRequest`。转换结果最终决定发送内容，被删除的参数不再补回。该合并仅涉及 query，不与请求体合并。

例如原查询参数 `id=1`，配置 URL `/custom/detail?id=2`，转换函数收到的查询参数中 `id` 对应配置 URL 的值。

实现约束：不能因自定义 URL 是否带 query 而悄悄改变同一接口的转换入参形状，也不能自动将请求体字段搬到 URL；完整接口清单需明确每个标识的参数通道。

## 执行顺序与实现边界

1. 从当前组件实例取得该业务接口配置，先判断同接口是否有既有执行器。有则仅执行执行器，不运行新配置或其转换。
2. 无执行器时，保留既有业务参数构造，解析该接口允许的参数通道和 URL query 优先级；未提供转换则沿用现有内容。
3. 提供请求转换时等待其完成，按接口契约验证结果后完整替换，不做隐式合并或补字段。
4. 使用既有方法、请求头、编码和传输通道发送一次请求；新 URL 同源校验须发生在实际发送前。
5. 提供响应转换时，等待并验证转换结果，再执行该接口既有成功判断、取值、正规化和业务动作。请求层未交给 service 的 HTTP 原始信息不承诺提供给转换函数。
6. 转换异常或无效结果终止该路径，不再走默认接口。返回原值须显式 `return input`，不是省略 return。

实现须保证异步操作始终属于发起它的实例，不在 await 后读取另一实例的配置。建议一次调用固定其配置引用与转换函数，后续配置变更仅影响后续调用；宿主不原地修改共享配置对象。此为保障实例隔离的实现建议，未要求新增配置更新 API。

零配置路径必须保持历史行为。新增转换校验、参数拆分与重建不得导致原先未配置的请求变成错误，或改变参数重复项、编码、文件字段、响应结构及错误提示。

- [ ] **参数通道限制**：对新增通道明确报错；同一接口的转换输入类型不随配置值动态变化。
