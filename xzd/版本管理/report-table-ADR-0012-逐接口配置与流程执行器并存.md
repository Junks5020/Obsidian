# ADR-0012：逐接口配置与流程执行器并存

用户在需求访谈中明确：`udp-report-table` 的业务接口均需支持 URL、请求内容与响应结果适配，未配置部分保持原有行为；同时保留读取设计、保存设计、计算预览三个既有流程执行器。决定采用实例级 `apiConfig`，以业务接口标识配置 `url`、`transformRequest`、`transformResponse`；同一接口存在 `apiExecutor` 时由执行器独占处理，新配置完全不参与。

本 ADR 记录已确认的架构取舍。用户于 2026-10-29 整体确认完整需求基线，包括不得新增原接口参数通道的限制；此确认不授权实施、提交或发包。文件细节、验证要求及边界见需求基线。

## 与 ADR-0011 的关系

ADR-0011 解决当时三个设计流程的完整请求接管，曾因语义重叠选择移除旧 `apiUrl/apiTransform`。本次需求扩大到组件包全部业务接口，包括打印、辅助查询、上传与导入导出；接入方只需改某一项时，不应被迫重写请求发送流程。因此重新提供受限的逐接口适配能力，但不恢复旧 prop，也不移除旧执行器。

此决策调整 ADR-0011 的“只保留执行器、无并列适配入口”选择；其三个执行器的契约及完整接管能力继续保留。旧 ADR 保留为历史，不静默覆写。

## 取舍

- **仅扩展执行器**：不能直接满足用户要求的按项覆盖、未配置项保留默认行为；接入方需要自行复写发送逻辑，不采用。
- **移除执行器，统一新配置**：会破坏既有接入，用户明确选择保留兼容，不采用。
- **将转换叠加到执行器外**：同一数据可能被重复转换，也会改变完整接管含义；用户选择执行器优先，新配置不参与。
- **采用受限适配与执行器并存**：接受双入口的文档与测试成本，换取渐进式定制和兼容性。优先级必须可测试、可解释。

## 约束与后果

- 配置按实例隔离，不依靠修改全局请求对象或共享配置来切换不同实例。
- 新配置只开放 URL、请求内容、响应适配；方法、请求头、参数通道和编码方式保持既有行为。不得新增原接口没有的参数通道，例如仅 body/FormData 的接口不可经自定义 URL 新增 query，违规配置应明确报错。既有执行器不受这些新限制。
- 新 URL 仅同源，跨域通过同源代理；不暗中扩大凭据发送范围。
- 请求转换结果完全替换，支持同步与异步。响应转换适配回各接口原有消费契约，不强制统一信封。
- 新配置失败不回退默认接口重发，避免重复写入或写入另一后端。
- 默认路径与自定义路径须双向验收：不能为了统一接口层而改变未配置场景下的参数、错误处理、文件传输或业务动作。
