# 附件打包下载默认名现场诊断

相关：[[../ng-design-附件术语表]] · [[../../代码提交记录/ng-design/变更记录/REQ-20261026-001-KAN-11-attachment-export-name]]

## 现场验证

在用户提供的表单页面，点击工具栏“附件”弹窗内“打包下载”，浏览器建议文件名为 `打包下载.zip`。点击前捕获的下载链接 `download` 属性同样为 `打包下载.zip`。下载地址路径中的后端文件名也是 `打包下载.zip`；未采集最终响应头。

现场加载的 formruntime JS 包含 `getAttachmentExportName` 等价逻辑，以及名称非空时添加 `.zip`、为空时使用默认名称的分支。首次仅捕获旧下载属性，无法严格区分空值回退与显式旧名称；此前认定必然进入空值分支不严谨。

页面地址中 `AppTitle` 为空，界面中的单据名称输入为空；这与名称缺失导致回退相符。未逐项读取运行时的 `exportName`、菜单名和表单值，无法对各取值逐一作实测断言。页面标签显示 `fujian`，是否作为菜单名兜底需业务确认。

## 设置名称后的复测

用户设置 AppTitle 与单据名称均为 `123123` 后，顶部附件弹窗打包下载时捕获 `link.download` 为 `123123-123123.zip`，浏览器建议下载名却仍为 `打包下载.zip`。实际下载地址中的后端文件名仍为 `打包下载.zip`。对同一地址 GET 返回 HTTP 200、无重定向，响应头 `Content-Disposition` 指定 `attachment; filename="%E6%89%93%E5%8C%85%E4%B8%8B%E8%BD%BD.zip"`。该响应命名与最终旧名吻合，解释了前端下载建议名被覆盖的现象。断点未捕获单项运行时值，不作逐项断言。

## 本地修复

用户确认后端参数为 `exportName`。当前 `liujinxu/exportName_explain` 工作区已将生成的无扩展名 `archiveName` 以 `exportName` 传入 `createZip`；保留前端下载属性。真实 handler 模拟回归先失败后通过，覆盖生成名、自定义名、空值、权限和业务 veto；尚未提交、部署。

## 后端接口实测

通过现场页面已有登录态和真实附件会话，在一次正常打包请求中临时注入 `exportName: 123123-123123-接口验证`，不改变其余请求字段。浏览器最终下载建议名为 `123123-123123-接口验证.zip`，下载 URL 的文件名一致；对该地址 GET 得到 HTTP 200、无重定向，响应 `Content-Disposition` 指定同一文件名。进度响应未被采集，因此不对进度响应字段作断言。临时拦截已恢复，未修改页面单据；本地代码仍待部署后整体验证。
