# 硕正报表第一阶段对接范围

相关：[[00-版本总览]] · [[ng-design-Agent工作流配置]] · [[work-items/report-table-functional-sync-refactor/spec]]

## 结论

已确认：第一阶段是前端阶段，不纳入后端接口开发。后端接口作为外部依赖，由前端整理请求/响应、鉴权和错误处理契约并进行联调验证；若发现接口缺失，记录为后续后端工作项，不在本阶段通过前端 Mock 冒充已完成闭环。

第一阶段目标不是一次性实现硕正全部原生 API，也不是在 `ng-design` 组件库中建设 `msgfi-frc` / `msgfi-gc` 业务菜单。第一阶段先交付两个前端可复用闭环：

1. 报表格式设计：宿主应用可以打开 `DesignReportTable`，加载、编辑、保存基础报表，并通过稳定的兼容入口完成常用编辑操作。
2. 打印数据交付：组件输出稳定的打印数据和使用方式，默认以 `pdfmake` 作为消费方；实际 PDF/打印实现由使用方完成。

业务应用路由、菜单权限、后端接口由 `msgfi-frc` / `msgfi-gc` 项目负责接入；本仓库第一阶段只提供组件、适配器、前端状态/权限行为和契约，不把业务页面或后端能力伪装成组件库能力。

## 第一阶段必须对接

### 1. 宿主接入契约（前端）

- 固定 `DesignReportTable` 的宿主参数：`id`、`name`、`type`、`isView`、`busPhId`、`exportAuth`、`headerToolbarCfg`、`handleToolBarAction`。
- 约定设计数据的加载、保存、导入、导出和错误处理回调；明确数据集请求地址、鉴权请求头和请求参数由谁注入。
- 明确 `ReportTableAPI` 的最小公共能力，不让业务方直接依赖 Handsontable 实例；保留 `getHotInstance()` 仅作为迁移兜底。
- 为所有新入口增加类型和边界测试，维持现有 `node:test` 测试体系。

后端接口只做契约消费和联调验证，不在本阶段新增、修改或迁移服务端接口。

### 2. 报表编辑基础 API 兼容层

第一阶段只做高频、可由当前设计器稳定承载的能力，统一封装到 `udp-report-table` 的 API 适配器中：

| 能力 | 第一阶段要求 | 实现依据 |
| --- | --- | --- |
| 行列计数 | 支持 `getRows()` / `getCols()` | Handsontable `countRows()` / `countCols()` |
| 行列增删 | 支持 `insertRows()` / `insertCols()` / `deleteRows()` / `deleteCols()` | Handsontable `alter()` |
| 行列显示 | 支持 `hideRow()` / `hideCol()` / `isRowHide()` / `isColHide()` | hiddenRows / hiddenColumns |
| 行列尺寸 | 支持 `setRowHeight()` / `setColWidth()` | 现有工具栏和右键菜单 |
| 单元格数据 | 支持 `setCellData()` / `getCellData()` | `setDataAtCell()` / `getDataAtCell()` |
| 单元格属性 | 支持 `setCellProp()` / `getCellProp()` / `setCellFont()` | cell meta 和现有样式工具栏 |
| 合并与选区 | 支持 `merge()` / `selectCell()` / `getCurrentCell()` | mergeCells 和 selection |
| 单元格读取 | 支持 `getCellText()` | 统一文本读取规则 |
| 基础显示调用 | 支持受控的 `callFunc()` / `setProp()` 子集 | 只暴露已验证的函数白名单 |

以下能力第一阶段不承诺同名兼容：`getFileXML()`、`setBatchFunctionURL()`、`getProp()`、`findCell()`、`addEditAbleOnly()`、`getCellRow()`、`getCellCol()`、`getCellName()`。如业务确有依赖，先补充调用样例和返回契约，再单独立项。

### 3. 工作表最小能力

报表设计闭环需要支持工作表的读取和当前页定位，第一阶段实现：

- `getWorksheets()`
- `getCurrentWorksheet()`
- 工作表名称读取

工作表新增、删除、重命名是否纳入第一阶段，取决于目标报表设计页面是否开放多 Sheet 编辑；在业务确认前不承诺 `setWorksheetName()` / `deleteWorksheet()` 的完整兼容语义。

### 4. 工具栏兼容入口

新增 `REPORT_TOOL_BAR_FUNC` 的兼容映射，但只覆盖第一阶段实际可用的功能：

- `PRINT_SETTING` → `print_setting`
- `PRINT_PREVIEW` → `print_preview` / `ribbon_preview`
- `UNDO` / `REDO` → `undo` / `redo`
- `CELL_MERGE` → `merge_cells`
- 行列插入、删除、行高、列宽 → 现有工具栏/右键菜单动作
- 导入、导出 → `report_import` / `report_export`

`NEW_REPORT`、`SAVE_AS`、查找替换、公式弹窗、统计图、数据源弹窗、计算器、显示开关等没有稳定对应物，第一阶段不做空壳常量；需要时按真实交互单独补充。

### 5. 报表权限最小模型

为宿主提供 `REPORT_LIMIT` 的最小兼容配置，至少覆盖：

- `FORMULA`
- `NON_FORMULA`
- `WORKSHEET_ADD_AND_DEL`
- `ROW_CLO_ADD`（沿用原需求中的常量名；如实际接口为 `ROW_COL_ADD`，在适配层做别名）

权限必须在工具栏、右键菜单和 API 三个入口同时生效。组件级 `readOnly` / 设计器级 `isView` 只能作为总开关，不能替代上述细粒度权限。

### 6. 打印数据契约与使用方式

第一阶段不交付打印引擎，不要求使用方接入 Supcan，也不把现有 `PrintPlugin` 五个 API 作为必做验收项。组件需要提供：

- 可被宿主消费的稳定打印数据结构。
- 单据数据、表格数据、模板标识和业务主键的使用说明。
- 默认 `pdfmake` 消费示例或文档，说明如何将打印数据组装为 `documentDefinition` 并导出 PDF。
- 数据缺失、模板不存在和转换失败时的前端错误状态。

现有 `PrintPlugin` 保留为旧引擎兼容能力和迁移参考，单独标注 Supcan 依赖；不作为第一阶段打印实现路径。

## 第一阶段业务落点

组件库完成后，由业务应用按以下顺序接入：

| 优先级 | 菜单/路由 | 第一阶段处理 |
| --- | --- | --- |
| P0 | `/frc/reportForm/form` | 接入报表格式设计；验证加载、编辑、保存、权限和导入导出 |
| P0 | `/frc/report/batchPrint/printPlan` | 接入打印方案数据配置；验证模板数据、打印属性和 PDF 消费数据输出 |
| P0 | `/frc/report/batchPrint/list` | 前端只输出既有业务数据和使用方式；实际批量打印由业务应用使用 `pdfmake` 等方案实现 |
| P1 | `/frc/report/list`、`/frc/projectReport/list` | 先完成列表/详情宿主页面，再复用设计器/预览组件 |
| P1 | `/gc/accountBookManage/list`、`/gc/voucher/list`、`/gc/voucher/detail` | 先确认凭证/档案打印数据契约，再接入通用打印 |
| P2 | 批量计算、表间校验、合并报表、合并底稿、抵销分录、周期凭证 | 不属于组件库第一阶段，需业务应用和后端专项实现 |

## 明确不纳入第一阶段

- 15 个业务菜单的完整路由和页面实现。
- 硕正全部原生 API 的同名兼容层。
- 公式解析、用户函数、实时计算、跨表校验的完整引擎。
- 原生事件订阅和事件锁：`subscribeEvent()`、`enableEventLock()`、`eventLock()`、`eventUnLock()`。
- 完整工作表原生 API：工作表新增/删除/重命名的全部边界语义。
- `PrintPlugin` / Supcan 打印运行时的第一阶段接入。
- 组件内部完整 PDF 排版、浏览器打印和打印机适配；默认由使用方基于 `pdfmake` 实现。
- `getPrintPages()` 和其他独立打印引擎 API。
- `setHttpHeadProp()`、`setAutoCalc()`、`setRedrawAble()` 等已标记去掉/暂不需要的接口。

## 验收标准

1. 宿主可用一个稳定的 `DesignReportTable` 接入完成报表设计闭环，业务代码不直接调用 Handsontable。
2. 第一阶段 API 的类型、运行时导出、权限和工具栏映射均有边界测试；现有测试保持通过。
3. 报表设计和打印方案两个 P0 路由具备可复现的前端加载、保存、预览和失败状态处理；真实接口依赖单独记录联调结果。
4. 打印数据结构、模板/业务主键传递、`pdfmake` 消费方式和失败状态有前端验证；Supcan/PrintPlugin 仅作为兼容文档，不计入第一阶段完成条件。
5. 未纳入能力在接口文档和业务接入清单中明确标为“未支持/待确认”，不以底层等价调用冒充硕正原生兼容。

### 测试边界

- 使用现有 `node:test` 验证 `formdata + Grids` 数据结构、类型和序列化契约。
- 使用组件边界测试验证公共导出、工具栏映射、`REPORT_LIMIT` 前端拦截和未支持 API 清单。
- 执行 TypeScript 检查和包构建，验证示例代码可以消费打印数据。
- 不做 PDF 像素比对，不做 Supcan 运行时测试，不做浏览器打印端到端测试。

## 已确认的阶段边界

- 交付主体：前端组件、前端适配器、工具栏/权限交互和联调验证。
- 后端范围：不开发新接口；只确认现有接口可消费，并输出缺口清单。
- 验收方式：前端测试 + 既有接口联调；未就绪的后端能力不得用 Mock 计入完成。
- 页面边界：本仓库不实现 `msgfi-frc` / `msgfi-gc` 业务路由；路由仅作为组件消费方验收场景。
- API 边界：只实现 P0 场景所需的最小兼容 API 集合；未支持 API 保留清单，不以底层等价能力冒充完成。
- 权限边界：`REPORT_LIMIT` 只做前端交互控制；后端现有鉴权仍是最终授权来源，本阶段不新增服务端权限校验。
- 公式边界：只保证公式字段保留、读取和编辑兼容，不实现公式解析、用户函数或设计时实时计算。
- 打印依赖边界：`pdfmake` 不作为组件库运行时依赖，只提供打印数据类型、数据结构和使用示例。
- 打印展示边界：不提供 PDF 预览、下载或浏览器打印 UI；这些由业务应用基于所选打印引擎完成。
- 打印数据契约：沿用现有 `formdata + Grids` 结构作为第一阶段稳定输入，不重新设计新的打印数据模型；只补齐类型、字段说明和 `pdfmake` 转换示例。
- 打印 API 边界：提供 TypeScript 数据类型和独立 `pdfmake` 使用示例，不新增公共 `buildPdfMakeDocumentDefinition()` 导出。

## 待业务确认的问题

- `setSource()`、`setParasEx()` 需要由谁提供参数，是否要对宿主公开。
- 报表设计是否必须支持多 Sheet 新增、删除、重命名。
- 打印数据中模板标识、业务主键和 `Grids` 命名由哪个业务应用提供；第一阶段只消费既有结构。
- `/frc/report/list`、`/frc/projectReport/list` 等业务页面的接入排期由对应业务项目负责。
