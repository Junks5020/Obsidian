## 2. 用户现象与兼容目标

用户反馈：

> 自定义表单明细表里的附件，第一次打开存在，再次打开就消失；把 `code` 改回原来的 `guid,asrCode` 后可以正常显示。

1. 明细行关闭重开、切行后，仍使用正确的业务关联键与会话 GUID 初始化附件。

## 4. 当前渲染与数据链路

### 4.1 明细入口和字段分类

- `pageComponent/customFormNew/detail/grid.tsx`：`Grids` 将 `stateData[grid.name]` 交给移动端 `Table`；保存取明细数据时调用表格实例的 `getChange()`。
- `component/Table/table.tsx:147–180`：表格单元格主要显示“附件”，普通列附件从 `guid@@数量` 提取数量；不在此处用 `res.asrCode` 直接渲染文件列表。
- `component/Table/table.tsx:870`：构造明细编辑字段时，对附件编辑器设置 `nameField = item.name`。
- `component/Form/index.tsx:55、405–445`：系统 `code` 会话附件按非列附件处理，`colAttach='0'`，表名为绑定业务表；普通字段附件通常使用 `colAttach='1'`、`asrtable='system'`。

因此，**“位于明细表中”不代表一定是列附件**。本次问题的重点是明细行里的系统 `code` 会话附件。

### 4.2 初始化请求与列表来源

`component/Attachment/attachment.tsx:118–146` 从绑定值计算内部 `asrCode`：

| 绑定值 | 初始化使用的内部 `asrCode` | 会话 GUID 的提取 |
| --- | --- | --- |
| `guid,asrCode` | 逗号后部分 | 逗号前部分 |
| `guid;asrCode` | 分号后部分 | 分号前部分 |
| `guid@@数量` | `@@` 前部分 | `@@` 前部分 |
| 纯 GUID 或纯业务键 | 原字符串 | 当前 `getGuidInValue` 返回 `''` |

`component/Attachment/attachment.tsx:219–268` 调用初始化接口后：

- 从 `res.asrSessionGuid` 设置 `state.guid`。
- 从 `res.fileList` 设置附件列表，必要时请求预览 URL。
- 最终将 `state.fileList` 传给 `AttachmentList` 或 `AttachmentTypeList`。

`component/Attachment/api/service.ts:32` 请求 `/JFileSrv/reactAttach/appAttachInit`。请求类型 `api/attachemntInit/request.ts` 的字段转换为：

```text
组件 init 参数 value       → HTTP 参数 asrCode
组件 init 参数 sessionGuid → HTTP 参数 asrSessionGuid
组件 init 参数 asrtable    → HTTP 参数 asrTable
```

**本组件不是直接依赖初始化响应中的 `res.asrCode` 渲染附件；查询键来自绑定值解析，文件列表来自响应。** 探针响应即使提供 `asrCode: 'record-phid'`，也没有阻止回写时丢失原业务键。

### 4.3 初始化本身就会回写，不需要用户上传或删除

`component/Attachment/attachment.tsx:268` 在初始化得到非空附件列表时更新 `fileList`。随后 `:355–384` 的列表变更 effect 执行：

```ts
if (!editRef.current && !state.fileList.length) {
  return;
}
// ...
onChange?.({ value: handledValue, label: state.fileList });
```

列表非空即会越过该判断。因此，“打开查看一下再关闭”已经足以将新的 `handledValue` 回写进表单。

### 4.4 回写如何进入明细行，并在重开时生效

```text
Attachment 初始化得到非空 fileList
  → 文件列表 effect 触发 onChange({ value, label })
  → Form.handleValuesChange / syncValues
  → 更新 defaultValue 及明细编辑行数据
  → Table.onPopupClose 将 updateRef.current.formValue 写回 ds[curIndex]
  → 关闭弹窗并销毁内部组件
  → 再打开时，由保存的明细行数据创建新 Form / Attachment
  → 用回写后的 code 重新计算初始化参数
```

源码依据：

- `component/Form/index.tsx:215、259、642`：初始化值、同步值和字段变更处理。
- `component/Form/util.tsx:11`：`getInitValues` 对传入对象直接返回；与表单转换一起形成明细行的运行态引用链。
- `component/Table/table.tsx:1104–1113`：`onPopupClose` 写回当前编辑行。此处明确不调用表单提交方法，不能把它误认为已经进行业务保存。
- `component/Table/table.tsx:1504–1523`：明细行 Form 的值与 `onValuesChange` 回写。
- `component/Table/table.tsx:1573–1583`：弹窗受 `curIndex > -1` 控制，并设置 `destroyOnClose`。

## 5. 问题一：纯 GUID 回写导致重开丢失业务键

### 5.1 上次修改改变了运行态数据格式

`62e9292e3` 将非列附件回写从：

```ts
res = `${guid},${asrCode}`;
```

改成：

```ts
res = guid;
```

对应当前 `component/Attachment/attachment.tsx:171–186`。

这不只是改变保存格式，而是改变了组件每次 `onChange` 回写到明细行中的运行态绑定值。原业务键被丢弃后，重新挂载的组件不能只靠纯 GUID 还原第一次的初始化参数。

### 5.2 当前版本的实际前端测试记录

初始明细行：

```json
{
  "phid": "record-phid",
  "code": "session-guid,record-phid"
}
```

| 阶段 | code / 回写值 | 初始化业务键 | 初始化会话 GUID |
| --- | --- | --- | --- |
| 第一次打开 | `session-guid,record-phid` | `record-phid` | `session-guid` |
| 初始化列表加载完成 | 回写 `{value: 'session-guid', label: [...]}` | 当前实例暂时继续使用原会话 | 当前实例暂时继续使用原会话 |
| 关闭明细行 | 行数据中仅保留纯 GUID 绑定 | — | — |
| 再次打开 | 从纯 GUID 重新解析 | **`session-guid`** | **`''`** |

本地最小化还验证了初始行只有 `{phid: 'record-phid'}`、没有 `code` 的情况：Form 首次会用主键补值，首次查询正确；列表加载后同样回写纯 GUID，重开同样丢失业务查询键。

整个用例无需上传、删除或保存业务单据。

### 5.3 为什么上次的回声保护没有覆盖重开

`component/Attachment/attachment.tsx:63、374–423` 的 `emittedBindingValueRef` / `initializedBindingRef` 可以识别**同一挂载实例内**的 onChange 受控回填，避免立即重新初始化。

明细弹窗关闭销毁组件后，这些 ref 随实例结束；重新打开的组件没有历史映射，因而仍按纯 GUID 重新计算业务键。保护了“本次打开”，不等于保护了“下一次打开”。

## 6. 问题二：明细保存会把纯 GUID 清空

当前明细保存取值链路为：

```text
Grids.getGridData
  → Table.getChange / getAllData
  → getStore / getData（将 value/label 对象展开成 value）
  → _getResultTable
  → filterRowByBusFields
```

`component/Table/table.tsx:684`：

```ts
newData.code = getGuidInValue(newData.code) ?? newData.code;
```

`component/Attachment/util.ts:104–116` 的 `getGuidInValue` 只在包含分隔符时提取 GUID；对不带分隔符的非空字符串返回 `''`。

因此：

```text
getGuidInValue('session-guid') === ''
'' ?? 'session-guid' === ''
```

| 保存前 code | `getData` 展平后 | `filterRowByBusFields` 后 |
| --- | --- | --- |
| `{value: 'session-guid,record-phid', label: [...]}` | `session-guid,record-phid` | `session-guid` |
| `{value: 'session-guid', label: [...]}` | `session-guid` | **`''`** |

这段表格保存逻辑在回归提交之前已经存在，**不是 `62e9292e3` 新写的解析缺陷**；该提交改变输出格式后，把原来的兼容缺口带入了实际明细路径。

### 补充：Form.beforeSubmit 也存在纯 GUID 兼容缺口

`component/Form/index.tsx:753` 对 `isCodeAttach` 的 value/label 对象直接执行 `getGuidInValue(originValue.value)`，也可能清空纯 GUID。

该专项在父版本和当前版本都失败，属于既有问题。本次探针对该辅助用例使用不带 `nameField` 的表单字段配置，以独立检验解析行为；**不能把这个辅助结果当作当前明细弹窗关闭时实际调用了 `beforeSubmit` 的证据**。当前明细的主要保存证据来自上面的 `getData → filterRowByBusFields`。

## 8. 修复建议：同时兼顾重开与保存，但本次未实施

### 8.1 分离运行态关联信息与持久化格式

优先明确两个不同的契约：

- **运行态**：跨明细弹窗销毁/重建，必须能恢复正确的业务 `asrCode` 与附件会话 GUID。可以保留复合绑定，也可以由明细行或上层稳定上下文独立携带两者，但不能只放在 Attachment 实例 ref 里。
- **保存态**：提交系统 `code` 时提取 GUID；输入已经是纯 GUID 时原样保留，不携带 `,asrCode`，也不清空。

本次“手动保留复合值”的对照已证明：**明细路径可以在运行时保留 `guid,asrCode`，而在提交时输出纯 GUID。** 这不是主表、旧版表单、所有公开调用方都已验证的通用补丁。

若要求 `onChange` 本身也只能返回纯 GUID，则应为业务键增加独立的稳定传递途径，并验证保存后重新加载如何恢复关联，不能只恢复旧返回值。

### 8.2 不应采用的简单修改

1. **不能只修改表格保存的 `??`**：能避免保存清空，却恢复不了已丢失的业务键，关闭重开仍错误。
2. **不能只恢复一个实例内 ref 缓存**：弹窗销毁后缓存丢失。
3. **不能不加区分地把 `getGuidInValue` 全局改成返回原字符串**：初始化时的纯字符串也可能是业务主键；这会把业务主键误传成 `asrSessionGuid`。
4. **不能无范围地回退整个附件组件的输出格式**：自定义表单主表的 `formatValue`、旧版表单及其他调用方保存入口也需要核对，否则可能重新提交 `guid,asrCode`。
5. **不能仅从附件记录的 label 或文件列表恢复业务键**：应以明确的绑定/上下文契约为准，空附件列表也必须能稳定工作。

建议在保存边界单独定义“提取 GUID，已经是 GUID 时保留”的规范化行为；初始化仍区分业务键与会话 GUID，避免一份字符串解析函数承担两种不同语义。

### 8.3 后续验收清单

- [ ] 旧复合 code：仅查看、不上传/删除，连续关闭重开仍显示附件。
- [ ] 只有业务主键、没有 code：首次补值后连续重开仍使用正确业务键。
- [ ] 纯 GUID 输入：有明确业务键来源，不把主键误作会话 GUID。
- [ ] 切换明细行、弹窗销毁重建、业务表或业务类型变更不串附件。
- [ ] 上传、删除、删空后重传保持同一有效会话，不触发初始化循环。
- [ ] 明细保存请求的 code 为正确 GUID，不带复合后缀、不为空。
- [ ] 主表、旧版表单和其他公开入口继续满足各自保存契约。
- [ ] 保存并重新加载页面后仍能恢复关联；不能只测未保存时的弹窗重开。
- [ ] 普通列附件 `guid@@数量` 的关联、数量、保存格式不变。
- [ ] 后端实测两次初始化、上传、保存及重新加载请求，核对 `asrTable/asrCode/asrSessionGuid`。
- [ ] 核对现场部署资源确实包含 `62e9292e3` 及本次所查实现，再将本地回归与现场故障完全闭环。
