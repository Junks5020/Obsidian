# ADR-0001：跟随上游（6.5.2-dev）做功能型同步，包括跟随移除

相关：[[report-table-同步术语表]] · [[report-table-6.5.2-7.0-功能同步计划]] · [[report-table-功能型同步架构重构计划-20260810]]

udp-report-table 是 report-web 报表组件的 7.0 抽离包。我们决定：**以 report-web `6.5.2-dev` 为上游做单向功能型同步——上游的新增、修复、移除都跟随**，按功能血缘判断跟随范围（血缘在上游的功能即使被 7.0 小幅扩展过也跟随；7.0 原生功能不参与同步）。理由：同步的意义就是让 7.0 与 6.5.2 能力对齐；若因"本地改过"而滞留上游已召回的功能，同步规则即失效，且 7.0 会携带上游已判定有问题的代码首发。

## Consequences

- 首次应用（2026-08-05，ng-design `14bfbf811`）：跟随上游 `c6210ffc`（当时仅本地提交、未推送 origin）移除预览表格休眠接线、预览右键「隐藏当前行/列」、预览态强制分页行头标记；其中预览行列隐藏在 7.0 曾被增强（列压缩至 20px、支持列隐藏），一并撤除。同时移植该提交新增的「单元格内容溢出时 title 悬浮显示」。
- 唯一有意偏离：7.0 抽离期已有的卸载 `destroy` 清理保留（上游移除时连带丢失，组件包反复挂载/卸载会泄漏）。
- 上游移除时未清理的残余（store 字段、prop 声明等）在 7.0 侧按"同步"口径保持一致，不做额外清理也不保留死代码接线。
- 上游是移动目标（曾发生 rebase 与本地未推送提交）：每次同步任务以 `origin/6.5.2-dev` 为基准核对，本地未推送提交单独确认后再跟随。

## 重构验收基线（2026-08-06）

- 有上游功能血缘的行为，以 `report-web:6.5.2-dev` 的 parity fixtures 为验收基线。
- 7.0 原生行为，以当前 `ng-design` 的 characterization tests 为验收基线。
- 重构期间发现的既有功能错误单独登记为 bug，不夹带修复，避免把架构调整变成隐含功能修改。

## 架构重构范围（2026-08-06）

采用分阶段范围，避免一次重构跨越多条功能血缘：

1. 先深化报表树拓扑模块。
2. 再深化筛选提交与预览可见性模块。
3. 轴向无关的筛选计算本轮只调查功能血缘；确认横向路径属于上游行为且当前可达后，再决定是否实施。

每个实施阶段必须独立通过上述双基线验收，不以横纵对称为理由新增行为。

## 重构接口边界（2026-08-10）

- 新模块先作为 `udp-report-table` 包内实现边界，不从 `src/index.tsx` 导出。
- 不改变现有 props、事件或数据结构。
- 报表树拓扑模块提供包内纯查询接口，不直接修改 Handsontable、store 或 cell meta。
- 筛选提交与预览可见性模块通过包内 adapter 执行副作用，对外调用入口保持不变。
- 旧调用点逐个迁移，全部迁移并通过双基线验收后，再删除重复实现。

## 报表树拓扑生命周期（2026-08-10）

- 拓扑模块使用可重建的不可变快照，不持有 Handsontable、store 或其他 UI 运行时状态。
- `createTreeTopology({ configuredRows, responseCells })` 统一合并并标准化配置树元数据与响应 cells，提供节点、父子索引、范围证明和 `showLevel` 查询。
- sheet 数据加载后重建快照；第一阶段不增加全局缓存或新的 `WeakMap`。
- 折叠状态继续由 tree adapter 管理，拓扑模块只负责解释树事实。

## 筛选事务语义（2026-08-10）

- 本轮事务化只封装现有成功路径：延迟、开启 loading、计算筛选结果、重载表格设置、重建树状态、应用当前筛选 owner、render、关闭 loading。
- 不在架构重构中新增失败回滚、重试或吞错逻辑。
- 是否应保留全部 visibility owners 必须先由上游 parity fixture 证明；若现状错误清除其他 owner，单独登记 bug 并独立修复。
- store 与 Handsontable 操作经由包内 adapter 注入，以便验证调用顺序，但不改变对外行为。

## 轴向无关筛选的实施门槛（2026-08-10）

候选三只有同时满足以下条件，才可从调查转为实施：

1. 可达性：证明 UI 能形成 `expand === 'right'`，并记录从筛选入口到 `renderCol` 的完整调用路径。
2. 功能血缘：在 `report-web:6.5.2-dev` 找到对应实现或明确需求依据。
3. 行为基线：建立横向筛选 parity fixtures，覆盖单条件、多条件、重置及与持久隐藏列叠加。

任一条件不满足，本轮不抽象纵横算法，只记录证据、结论和再次评估的触发条件。

## 重构测试策略（2026-08-10）

- 沿用现有 `node:test`，不引入新测试框架。
- 拓扑模块测试输入输出契约：来源合并优先级、父子推断、断裂树、`showLevel` 和筛选范围证明。
- 筛选事务测试最终 cells 与隐藏集合；仅对影响行为的必要副作用顺序做断言。
- 公共边界测试继续保证 `src/index.tsx` 的运行时导出不变。
- 先补 characterization/parity fixtures，再迁移实现；每个迁移提交运行聚焦测试，每阶段结束运行全部四个现有测试文件与 TypeScript 检查。

## 重构期间的上游基线（2026-08-10）

- 开工时记录 `origin/6.5.2-dev` 的确切 commit SHA，整个重构以该 SHA 作为固定 parity 基线。
- 本轮计划固定 SHA 为 `6636f93207d701517e78de9af46cc8dd57548fda`；目标代码起点为 `ng-design:sync_branch` 的 `2114199ab95244262404e76ac8776aca3b0fa0d2`。
- 两个实施阶段之间不夹入新的上游同步提交。
- 每阶段完成后，单独检查固定 SHA 之后涉及树、筛选或可见性的上游提交。
- 如有相关变化，先保持当前阶段绿色，再用独立同步提交跟进，并更新基线 SHA 与 fixtures。
- 计划与提交说明同时记录基线 SHA 和功能血缘。

## 重构提交粒度（2026-08-10）

1. 固定上游 SHA，补齐重构前 characterization/parity fixtures。
2. 新增纯 `TreeTopology`，暂不迁移调用点。
3. 将 tree renderer 迁移到拓扑模块。
4. 将筛选范围判断迁移到拓扑模块。
5. 删除重复的树解释逻辑。
6. 为筛选成功路径补事务测试与 Handsontable adapter。
7. 抽取筛选提交 orchestration，并迁移现有入口。
8. 删除旧的分散提交逻辑。
9. 单独提交候选三的血缘调查结论；只有三道门槛全部通过，才另开实现提交。

每个提交必须独立通过对应测试并可单独回退，不在分支历史中保留跨提交的红灯状态。
